# PIA Intern System — Seed Data Guide

## Current layout of seed data + how to build the full relief set

Two purposes: (1) what exists today and exactly how, (2) how to produce a large,
realistic, fully-populated database covering every table/log/display.

---

## 1. How seeding currently works

Three separate mechanisms, which is important because the new full seed must decide
where each piece lives:

1. **EF `HasData`** in `AppDbContext.OnModelCreating` (lines 271–310) — baked into
   migrations. Only seeds the *static reference data*:
   - `Departments`: Id 1 "ERP Section" (ERP), Id 2 "Cyber Security" (CYBER), both with
     lat/long + RadiusMeters=100.
   - `Users`: one admin user (Id 1, username `admin`, password = demo admin password
     in `docs/DEVELOPMENT_CREDENTIALS.md`, role Admin).
   - `Shifts`: 1 Morning (09–17), 2 Afternoon (13–21), 3 Night (21–05), all
     `IsCompanyWide=true`, company-wide.
   - `AttendanceSettings`: single row (Id 1, GraceMinutes=15, ThresholdPct=80).
2. **API calls + `sqlcmd` scripts** (done ad-hoc during development) — created the
   mentors, interns, and their attendance; reset passwords; set dates.
3. **Seeder scripts** in `/tmp/opencode/` (e.g. `seed_attendance.py`) — inserted SQL rows
   directly (PDC attendance with OutTime/IsInRange/FaceVerified/statuses).

So today **only reference data is committed in code**; everything else is a mix of API
and raw SQL that lives outside the repo. A full seed for hundreds of interns should be
**one idempotent SQL script** (see §3), not HasData.

## 3. Target full seed (new version)

### 3.1 Audience goals (from session)
- **≥15 interns per department**
- **up to 12 departments**
- **6 mentors per department**
- **2 signatories (DepartmentHeads)** per department (certificate signatories)
- Every fillable field populated with relevant, realistic data:
  device binding, face enrollment, start/end dates, tasks + statuses, document uploads,
  gate pass / ID card / certificate requests and their states.
- All tables, logs, and displays functional against the data.

### 3.2 Target scale (chosen defaults)
- **12 departments**, e.g.: ERP Section, Cyber Security, Software Development, Data Science,
  DevOps & Cloud, QA & Testing, UI/UX Design, Mobile Development, Database Administration,
  Network Operations, Business Analysis, AI/ML Research.
- **6 mentors per department** × 12 = **72 mentors**.
- **≥15 interns per department**: use **18–20 per department** to comfortably exceed 15
  → **~220 interns**. (Mentor:intern ratio ≈ 1:3 — realistic.)
- **2 DepartmentHeads (signatories) per department** × 12 = **24 signatories** (pick two
  senior mentors per dept as heads; keep them also as mentors).
- Distribution across statuses (see §5.7) so every screen/rollup shows variety.

## 5. Design rules for the full seed

### 5.1 Delivery: one idempotent SQL script (chosen)
- File, e.g. `backend/InternSystem.API/Seed/full_seed.sql` (or `database/seed/full_seed.sql`).
- **Deterministic Ids** up front via a numbering convention so FKs resolve:
  - Departments 1–12
  - Shifts 1–3 company-wide, 4+ per-dept
  - Mentors grouped per dept: dept `d` → mentor ids `d*6-5 .. d*6`
  - Interns grouped per dept: dept `d` → interns `d*20-19 .. d*20`
  - Users seeded alongside (1 user per mentor + 1 per intern).
- **Idempotent**: `IF NOT EXISTS (SELECT 1 FROM Departments WHERE Name=...)` guards and/or a
  top-level `DELETE` of child tables in FK-safe order, then insert. `DBCC CHECKIDENT` reset
  where needed.
- **Runnable** with sqlcmd: `/opt/mssql-tools18/bin/sqlcmd -S localhost,1433 -U sa -P '<pw>' -C -i full_seed.sql`.

### 5.2 Password hashing (critical)
- BCrypt hashes are per-password salts — **cannot be generated inside plain SQL**.
- Approach: the script stores a **single known BCrypt hash constant** for a shared demo
  password (e.g. BCrypt hash of the corresponding demo password in
  `docs/DEVELOPMENT_CREDENTIALS.md` for interns, mentors and the admin), reused across rows. Fine for a demo DB since all dev interns share one password.
- Alternatively, generate the hashes with `dotnet`/`bcrypt` once and paste the literals into
  the script.

### 5.3 Dates window
- Pick a coherent demo window, e.g. **2026-06-01 → 2026-12-31** for most interns; vary
  StartDate/EndDate per intern (some already ended → certificates; some active; some
  starting soon). Interns' StartDate ≤ EndDate; EndDate is past (cert-eligible), current,
  or future.

### 5.4 Coordinates / geo
- Departments get real-ish office coordinates (slightly varied lat/long around a campus).
- `Attendances` Latitude/Longitude set near the department center; `IsInRange` true for most,
  a handful false (out of range → PendingReview path); `DistanceMeters` consistent with
  IsInRange.

### 5.5 Sample files (chosen: include real files)
- Create a seed uploads folder mirroring the `FileService` layout under the configured
  `UploadPath` (default `{ContentRootPath}/uploads`):
  ```
  uploads/
    documents/{internId}/{Cnic|UniversityId|Resume}/sample.pdf & sample.jpg
    gatepasses/ sample.pdf
    idcards/ sample.jpg
    certificates/ sample.pdf
    faces/ sample-face.jpg
    signatures/ head_{id}.png
    pdfs/ sample.pdf
  ```
- DB path columns store the **relative** path the app expects (forward slashes, as
  `FileService` does `.Replace("\\","/")`; `GetAbsolutePath` re-reverses), e.g.
  `documents/15/Cnic/abc.pdf`, `signatures/head_1.png`, `faces/sample-face.jpg`.
- A small companion `.sh`/`.ps1` copies the sample files into the live uploads dir; DB rows
  reference them so PDF/image endpoints actually resolve.

### 5.6 Face enrollment spread
- Vary per intern:
  - ~30% `Approved` (FaceEnrolled=1, FaceEnrolledAt set, valid `FaceEmbeddingJson` of floats,
    FaceApprovedByUserId = an admin).
  - ~25% `Pending` (FaceEmbeddingJson present, FaceEnrolled=0).
  - ~20% `Rejected` (FaceEnrolled=0, FaceRejectedReason populated).
  - ~25% `NotEnrolled` (FaceEmbeddingJson=NULL, FaceEnrolled=0).
- FaceEmbeddingJson format must match what backend consumes — a JSON array of doubles, e.g.
  `[0.123, -0.456, ...]` of a fixed length.

### 5.7 Status distribution (spread across every enum)
Approximately:
- **Attendance**: majority Present/OnTime, some Early/Late/Pending / Absent / OnLeave rows,
  a few PendingReview (IsInRange=false). ~15–20 weekdays per intern × (2 rows: in+out where
  OutTime set) → realistic volume.
- **DocumentUploads**: no doc / Cnic approved / UniversityId pending / Resume rejected mix.
- **GatePasses / IdCardRequests**: Pending / Approved / Rejected spread; PdfPath set on
  approved.
- **Certificates**: spread across Pending / UnderReview / Approved (PdfPath+DepartmentHeadId
  set) / Rejected (with reason). Only cert-eligible interns (EndDate ≤ today & % ≥ threshold)
  should be Approved.
- **Tasks**: Pending / InProgress / Completed / Overdue; CompletedAt on completed; Deadline
  past for Overdue.
- **InternTransferRequests / InternShiftChangeRequests / MentorTransferRequests**: a handful
  at each lifecycle state (Pending, Endorsed, InternAccepted, Finalised, Rejected) so the
  transfer/approval screens have real content; keep finalised ones consistent with the intern's
  actual current mentor/shift.
- **ActivityLogs**: emit rows for the creation/action lifecycle (InternCreated, TaskAssigned,
  DocumentApproved, FaceEnrollmentApproved, CertificateApplied, etc.) matching the entity
  states so History screens look real.

### 5.8 Log consistency
Every seeded mutation should have a matching ActivityLog row (LogType + PerformedByUserId +
TargetInternId + DepartmentId + CreatedAt + Description) so Admin logs and timeline displays
are populated and internally consistent.

## 6. How to generate the script (recommended authoring method)

Because the data is deterministic and error-prone by hand, generate it with code so relational
consistency is guaranteed:

1. Author a small generator (Python or a console tool) that models departments → mentors →
   interns → attendance → tasks → documents → requests, assigns statuses via a seeded RNG
   (fixed seed for reproducibility), and **emits the complete SQL** (INSERT statements +
   BCrypt literals) plus the sample-file copy commands.
2. Output: `full_seed.sql` + instructions to run it (or auto-run via sqlcmd).
3. Verify: run the sqlcmd count query (§7 below) before AND after to confirm every table is
   populated; spot-check a couple of interns' rolls (attendance %, cert eligibility) match
   expectations.

This guarantees FK integrity (no orphaned rows) and consistent logs without manual SQL
transcription errors.
